Our stance

We're not selling AI and we're not against it. We're the people who read the terms, check the admin settings and write down the rules, so your principals can make an informed call.

What it is

A practical governance program, sized for a design firm

AI governance means deciding, in writing, which AI tools your firm uses, what information is allowed to go into them, who approves new tools, and how you check that vendors handle your data the way they say they do.

For a large enterprise that's a committee. For an architecture firm it should be a short policy, a one-page staff guide, a review process for new tools and someone accountable for keeping it current. That's what we set up.

Why it matters for architecture firms

Your firm holds more sensitive information than most

Architecture firms don't usually think of themselves as data companies. But the files on your server describe buildings, clients and ideas that others would pay to see.

Client confidentiality

Owner agreements and NDAs often restrict how project information is shared. Pasting a program document or client email into a public AI tool may already be outside those terms.

Building and security data

Floor plans, security layouts and systems drawings for institutional, government or private clients can be sensitive in their own right, regardless of any contract.

Design IP

Unbuilt concepts, competition entries and your firm's own details and standards are your work product. You should know whether a tool's terms allow it to retain or learn from them.

AI features inside tools you already use

Vendors are adding AI features to design, collaboration and file platforms. Some are controlled at the account or admin level. We check what's available and enabled in your environment before staff start relying on it.

Moving a live project archive off an aging file server

Client
[Architecture firm, name pending approval]
Size
[Staff count]
Services
Egnyte migration, file structure design

The situation

The firm's projects lived on a single on-prem file server that had grown for years, including the files of a smaller firm it had absorbed. Staff reached live projects through a mapped drive and rarely browsed the server directly.

What we did

  • Built a phased migration plan and task list before moving a single file
  • Reviewed the server folder by folder with the firm to decide what migrates, what gets archived and what gets deleted
  • Separated the firm's business operations folders (accounting, HR, legal, marketing) from project data so each gets its own permissions in Egnyte
  • Planned for Projects to become a top-level Egnyte folder instead of staying buried several levels deep

What we found along the way

The live projects folder was three levels deep and hidden from a normal Explorer view, reachable only through the mapped drive. A second folder with a similar name held old files that needed archiving, not syncing. And before moving anything, we checked whether CAD Xrefs and Revit links used absolute or relative paths, because absolute paths break when folder locations change.

Why this matters. A migration that copies folders as-is carries every old problem into the new platform. The review is where most of the value is.
